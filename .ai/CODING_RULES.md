# 1. Purpose

This document defines the coding standards and conventions that apply to every piece of code written for the MarginFlow project.

Every contributor and AI assistant must follow these rules without exception.

Consistency in code is as important as consistency in the product.

---

# 2. Language and Runtime

MarginFlow is a React application.

| Area | Technology |
|---|---|
| Language | JavaScript (ESM) |
| UI Framework | React 19 |
| Build Tool | Vite 6 |
| Package Manager | npm |
| Module Format | ES Modules (`type: "module"`) |
| Serverless | Node.js (Vercel functions) |

TypeScript is not currently used. Do not introduce it without a documented decision.

---

# 3. File Structure

The application currently lives in a small number of files.

```
src/
  main.jsx          ← All components and application logic
  styles.css        ← All styles
  labourSeedData.js ← Seed data only
  lib/
    supabase.js     ← Supabase client initialisation
api/
  read-invoice-ai.js ← Vercel serverless function
```

All new React components belong in `src/main.jsx` until a modularisation plan is documented and approved.

Do not create new files in `src/` without a documented reason.

---

# 4. React Conventions

### Components

* Use function components only.
* Component names use PascalCase.
* Each component has one clear responsibility.
* Keep components as small as practical.

### Hooks

* Use built-in React hooks (`useState`, `useEffect`, `useMemo`, `useRef`, `useCallback`).
* Custom hooks are named with the `use` prefix.
* Avoid deeply nested hook logic. Extract to named functions.

### State

* Prefer local state for UI concerns.
* Prefer lifting state for data shared between components.
* Do not use global state management libraries without a documented decision.

### IDs

* Use `crypto.randomUUID()` via the `uid()` helper for all new record IDs.
* Never use array indices as record identifiers.

---

# 5. Data and Storage

### localStorage

Data is stored in localStorage using the pattern:

```
marginflow.<module>
```

Examples:
- `marginflow.suppliers`
- `marginflow.products`
- `marginflow.invoices`

Always read and write using the helpers already defined in `main.jsx`. Do not add new storage keys without updating `cloudModuleDefinitions`.

### Supabase

Supabase is optional. Always check `isSupabaseConfigured()` before making Supabase calls.

Never assume Supabase is available. The application must function in local-only mode.

### IDs

Every record must have a stable `id` field generated by `uid()` at creation time.

---

# 6. Business Logic

* Business rules belong in logic functions, not inside JSX.
* Never perform financial calculations inline inside render.
* Every calculation must be reproducible and testable in isolation.
* GP, labour percentage and recipe cost calculations must follow the definitions in `docs/06 Business Rules/`.

---

# 7. Naming Conventions

| Type | Convention | Example |
|---|---|---|
| Components | PascalCase | `InvoiceList` |
| Functions | camelCase | `calculateGP` |
| Variables | camelCase | `invoiceTotal` |
| Constants | camelCase | `defaultDepartments` |
| CSS classes | kebab-case | `invoice-review-table` |
| localStorage keys | `marginflow.<module>` | `marginflow.invoices` |

Avoid abbreviations unless they are industry-standard (GP, VAT, SKU).

---

# 8. CSS Rules

* All styles live in `src/styles.css`.
* Use CSS custom properties defined in `:root` for colours and shared values.
* Do not use inline styles for values that belong in CSS variables.
* Do not use Tailwind or any CSS-in-JS library.
* New component classes follow the kebab-case pattern already used throughout the file.
* Dark theme is the only supported theme.

See `docs/04 UI/Design System.md` for the full design token reference.

---

# 9. AI and Serverless

* The AI invoice function lives at `api/read-invoice-ai.js`.
* The Anthropic API key is stored as an environment variable. Never hardcode API keys.
* AI functions must always return structured responses. Parse and validate before use.
* If AI extraction fails, the workflow must remain completable manually.

---

# 10. Error Handling

* Every async operation must have error handling.
* Errors shown to users must be human-readable, not raw exception messages.
* Silent failures are not acceptable. Log errors and surface them appropriately.
* Invoice processing failures must never leave the application in a broken state.

---

# 11. Dates

* All dates are stored as ISO strings (`YYYY-MM-DD`).
* Use the `today()` helper for the current date.
* Never use `new Date()` directly in business logic without formatting.

---

# 12. What Not to Do

* Do not introduce new dependencies without a documented reason.
* Do not use `console.log` in production paths.
* Do not use `any`-equivalent patterns that hide data shape.
* Do not modify `labourSeedData.js` — it is seed data only.
* Do not hardcode supplier names, product names or financial values.
* Do not bypass the invoice approval workflow.
* Do not create records without a `uid()`-generated `id`.

---

# 13. Code Reviews

Before submitting any change, verify:

* Does it follow the naming conventions in this document?
* Does it use existing helpers rather than duplicating logic?
* Does it handle errors?
* Does it preserve the existing data model?
* Does it follow the relevant business rules?
* Is it consistent with the rest of the codebase?
